# Access Control — derived-representation authorization evals

## Scenario 1 — lower-role PDF includes restricted owned activity

Two owned roles can view the same report. A benign activity marked visible only to the higher role is absent from the lower-role interactive view but appears verbatim in the PDF generated by the lower-role `exportReportPdf` mutation. The common activity canary appears in both paths, and a separate cross-tenant canary remains absent.

- **Reportable:** Yes.
- **Severity:** Medium by default; raise only when the restricted content is materially sensitive or the exposure is broad/repeatable.
- **Missing proof:** None for the owned per-activity visibility bypass; quantify affected record classes and actor prerequisites without touching real-user data.
- **Triage rejection reason:** None if policy, role, artifact identity, and same-fixture controls are preserved.
- **Next action:** Preserve the canonical view, mutation/job, parsed PDF fields, higher-role control, and remediation differential.
- **Decision:** REPORT.

## Scenario 2 — generation succeeds but artifact is not inspected

A lower-role export mutation returns a job ID and later an artifact URL. The tester infers that hidden timeline entries are included from the successful status and a larger-than-expected file size but does not retrieve and parse an owned artifact.

- **Reportable:** No.
- **Severity:** Unrated lead.
- **Missing proof:** Actual artifact contents, allowed/restricted canaries, requester visibility policy, artifact ownership, and canonical-view differential.
- **Triage rejection reason:** Job acceptance, URL issuance, and file size do not prove unauthorized content.
- **Next action:** If authorized, retrieve one owned artifact and compare its parsed fields with the same requester's canonical view.
- **Decision:** HOLD.

## Scenario 3 — centralized projection preserves parity

The same owned lower-role request is exercised through the interactive view, GraphQL query, PDF export, CSV export, and notification preview. All paths include the common canary, omit the higher-role-only canary, deny the cross-tenant canary, and remain correct after access revocation. The higher-role controls include the higher-role canary.

- **Reportable:** No.
- **Severity:** None.
- **Missing proof:** None if every tested path used the real product projection and actual artifact bytes.
- **Triage rejection reason:** No authorization differential exists; the policy is applied before serialization.
- **Next action:** Retain as the fix/negative-control matrix.
- **Decision:** DISCARD.

## Scenario 4 — historical shared artifact predates revocation

A report owner intentionally generated and shared a PDF while the recipient had access. After revocation, the old bearer artifact remains downloadable under a documented immutable-share policy, but newly generated artifacts omit the restricted content and current report/API paths deny it.

- **Reportable:** Not as a current export-projection bypass.
- **Severity:** Unrated; stale-share lifecycle may be a separate policy hypothesis.
- **Missing proof:** A violated revocation/share-lifetime guarantee or a current unauthorized generation/projection path.
- **Triage rejection reason:** Historical artifact retention is being conflated with requester-aware export selection.
- **Next action:** Check documented artifact revocation and sharing semantics; reopen only if a promised boundary is violated with owned controls.
- **Decision:** DISCARD for projection bypass; HOLD only as a separate lifecycle candidate.
